# agent foundation kit — სასტარტო ძრავა Claude Code-ის პროექტებისთვის

ეს არის მზა **სამუშაო გარემო** (ძრავა) ახალი პროექტისთვის, რომელსაც Claude Code აშენებს. თავად პროდუქტი აქ ჯერ არ არის — აქ არის ის, რაც უზრუნველყოფს, რომ აგენტმა ყოველ ახალ სესიაზე იცოდეს, სად გაჩერდით; არაფერი დაამტკიცოს შენს მაგივრად; საიდუმლო გასაღებებს არ შეეხოს; და ყოველი შედეგი მანქანამ შეამოწმოს. GitHub-ზე დააჭირე **Use this template**, და შენი ახალი პროექტი პირველივე დღიდან ამ წესებით დაიწყება. რას ვაშენებთ — [intent.md](intent.md); სად ვართ — [progress.md](progress.md); რა რიგით მივდივართ — [plan.md](plan.md); როგორ ვმუშაობთ და სად წყვეტ შენ — [process.md](process.md).

## როგორ მუშაობს — ერთი სურათით

წარმოიდგინე სამშენებლო ობიექტი, სადაც ბრიგადირი (Claude) ყოველ დილით მეხსიერებადაკარგული მოდის. რომ სამუშაო არ აირიოს, ობიექტზე ოთხი რამ არსებობს:

1. **მაგიდაზე დადებული დღის ფურცელი** — `progress.md`-ის „ახლა", `plan.md`-ის მიმდინარე ფაზა და `tasks/todo.md`-ის „ახლა / შემდეგი" (Claude-ის კონკრეტული დავალებები). Claude-ს ის ავტომატურად ეწოდება ყოველი სესიის დასაწყისში და ყოველი compact-ის (საუბრის ავტომატური შეკუმშვის) შემდეგ.
2. **სამუშაო ჟურნალი და არქივი** — ყოველ სესიას თავისი ჩანაწერი (ეპიზოდი) აქვს `memory/episodes/`-ში. სესიის ბოლოს `/session-close` ყველაფერს სწორ ადგილებზე ანაწილებს; თუ დაგავიწყდა, სესიის დახურვისას ფონური პროცესი თავად შეაჯამებს. მეხსიერების სრული რუკა — [memory/README.md](memory/README.md).
3. **შენი ხელმოწერა** — განზრახვა, სპეციფიკაცია (spec — ფუნქციის ზუსტი აღწერა), გეგმა და არქიტექტურული გადაწყვეტილება (ADR) ძალაში შედის მხოლოდ მაშინ, როცა შენ დაამტკიცებ `/approve`-ით. Claude-ს ამის გაკეთება არ შეუძლია — ამას guard (ავტომატური დარაჯი) ბლოკავს, gate კი ამოწმებს.
4. **ტექნიკური ზედამხედველი** — კარიბჭეები (gates — მანქანური შემოწმებები), რომლებიც ყოველ commit-ზე (შენახვის წერტილზე) და ყოველი პასუხის ბოლოს ეშვება და იჭერს იმას, რასაც მოდელი გამოტოვებს. თავად შემოწმებებიც მოწმდება: დრილი თითოეულს განზრახ „ტეხს" და ამოწმებს, რომ დაიჭირა.

ყველაფერი ჩვეულებრივი ტექსტური ფაილია, ერთმანეთთან ბმულებით — ამიტომ Obsidian-ში გრაფად ჩანს, Claude კი იმავე გრაფს `tools/context_graph.py`-ით ხედავს.

## როგორ დავიწყო — სამი ნაბიჯი

1. **შექმენი შენი პროექტი ამ შაბლონიდან.** GitHub-ზე, ამ გვერდის თავში, დააჭირე **Use this template → Create a new repository**, დაარქვი სახელი და ჩამოტვირთე კომპიუტერში (`git clone https://github.com/<შენი-სახელი>/<რეპოს-სახელი>.git` ან GitHub Desktop-ით).
2. **გახსენი იმ საქაღალდეში Claude Code** — ტერმინალში `claude` ან VS Code-ის Claude Code გაფართოება — და საქაღალდეს ნდობა მიეცი (trust). დანარჩენს ძრავა თავად აწყობს: git-ს, commit-ის შემოწმებებს და ხელსაწყოების შემოწმებას. setup-ის ბრძანებები არ გჭირდება.
3. **მისწერე შენი იდეა ჩვეულებრივი სიტყვებით** — მაგალითად: „მინდა გავაკეთო ვებსაიტი ჩემი საცხობისთვის: მენიუ, ფასები და ონლაინ შეკვეთა". ეს შეიძლება იყოს საიტი, თამაში, აგენტი, ავტომატიზაცია — ნებისმიერი რამ.

ამის შემდეგ Claude იდეას ჩაიწერს და ეტაპობრივად გაგიძღვება: ჯერ რამდენიმე კითხვა (განზრახვა), მერე ზუსტი აღწერა (სპეციფიკაცია), მერე — რით აშენდეს (არქიტექტურა), მერე გეგმა და აშენება, ბოლოს კი მუშა შედეგის ჩვენება. ყოველ ეტაპზე გეტყვის, რა მოდის შემდეგ, სტატუსის ზოლში (ეკრანის ქვედა ხაზები) კი 🧭-ით ჩანს, სად ხარ. მთავარ დოკუმენტებს Claude გთავაზობს, ძალაში კი მხოლოდ შენი ბრძანებით შედის — მაგალითად `/approve intent`; ზუსტ ბრძანებას ყოველ ჯერზე თვითონ გეტყვის. პროექტის ყოველ ტიპს — საიტს, თამაშს, AI აგენტს, ავტომატიზაციას და სხვას — თავისი სახელმძღვანელო აქვს (`docs/guides/`): მისი მიხედვით Claude გისვამს კითხვებს, გთავაზობს, რით აშენდეს, პირველ ვერსიას მცირე ზომისას ტოვებს და შედეგს გაჩვენებს.

### რა უნდა იყოს კომპიუტერზე

ძრავა ჯერ **Windows**-ისთვისაა აწყობილი (Windows 10 ან 11). საჭიროა **Git for Windows** (git-scm.com — მასთან ერთად დგება Git Bash, რომლითაც hook-ები, ანუ ავტომატური ჩამრთველები, ეშვება), **Python 3.12** (python.org; `py` ბრძანებაც მასთან ერთად დგება) და **Claude Code** შენი Claude-ის გამოწერით. თუ რომელიმე აკლია ან git-მა შენი სახელი და ელფოსტა არ იცის, Claude პირველივე სესიაზე გეტყვის და დაყენებას შემოგთავაზებს — შენი „კი"-ს შემდეგ. **gitleaks** (საიდუმლო გასაღებების მაძიებელი) სასურველია, მაგრამ აუცილებელი არ არის: მის გარეშე commit-ებს ძრავის საკუთარი, უფრო სუსტი სკანერი ამოწმებს და შედეგში ამას პირდაპირ წერს. სურვილისამებრ: **VS Code** (სამუშაოდ) და **Obsidian** (obsidian.md — პროექტის გრაფის სანახავად).

შემოწმება, რომ დაცვა მუშაობს: სთხოვე Claude-ს, `intent.md`-ის სტატუსი `accepted`-ზე თავად შეცვალოს — უარს მიიღებ `GUARD[G4]`-ით, და ასეც უნდა იყოს. ძრავის ყველა შემოწმება ერთად: `py -3.12 tools/gates/gate.py` (ბოლო ხაზი `GATES PASS`) და `py -3.12 tools/gates/drill.py` (~2 წუთი; `DEAD/DEFECT=0` — ყოველი შემოწმება ცოცხალია).

## ყოველდღიური მუშაობა

გახსენი ტერმინალი ან VS Code პროექტის საქაღალდეში და დაიწყე Claude — მან უკვე იცის, სად გაჩერდით. ჩვეულებრივად ესაუბრე. სტატუსის ზოლში 🧭-ით ჩანს, ხუთიდან რომელ ეტაპზეა პროექტი — განზრახვა, სპეციფიკაცია, არქიტექტურა, გეგმა და აშენება, ჩვენება — და რა არის შემდეგი ნაბიჯი, ხშირად ზუსტი ბრძანებით (მაგ. `/approve spec 1`). ეს ძრავის სამუშაო ციკლია ([ADR-0001](docs/adr/ADR-0001-foundation-and-sdlc-loop.md)); ზოლი მხოლოდ დოკუმენტების სტატუსებს კითხულობს ([ADR-0011](docs/adr/ADR-0011-idea-first-stage-conductor.md)). როცა ამთავრებ, თქვი „დავასრულოთ" (ან `/session-close`) — ის ჩაწერს, რა გაკეთდა, განაახლებს გეგმას და პროგრესს, გაუშვებს შემოწმებებს და შეინახავს. თუ სტატუსის ზოლში წითლად ანთია `↻3 ახალი სესია`, ესე იგი საუბარი სამჯერ შეიკუმშა — დროა `/session-close`, მერე ახალი ტერმინალი ან `/clear`.

მოდელს სესიის დასაწყისში ირჩევ (`/model`) და შუაში აღარ ცვლი; ერთი თემა — ერთი სესია. რატომ — ქვემოთ, „ქეში და ხარჯი".

## რა შეუძლია Claude-ს და რა არა

შეუძლია: ფაილების კითხვა და წერა, პროექტის შემოწმებების გაშვება, git-ში შენახვა ბრანჩზე (ბრანჩი — პროექტის ცალკე ასლი, რომელიც მთავარში შენი თანხმობით ერთიანდება). **ეკითხება შენ:** პროგრამების დაყენებას, ფაილების წაშლას, `git push`-ს და შერწყმას, თავად სამუშაო გარემოს (hook-ები, gate-ები, skill-ები, წესები, აგენტის ინსტრუქციები და გაკვეთილები) შეცვლას, ორკესტრაციის გაშვებას. **არ შეუძლია:** საიდუმლოების (`.env`) წაკითხვა, შემოწმებების გვერდის ავლა, ისტორიის გადაწერა, შენს მაგივრად დამტკიცება, სხვა სესიების ფაილების შეცვლა. გულწრფელად: ეს დაცვა „სიჩქარის ბორცვია" და არა სეიფის საკეტი — ამიტომ მის უკან მანქანური შემოწმებაც დგას და git-ის ისტორიაც. დეტალები — [ADR-0004](docs/adr/ADR-0004-harness-permissions-hooks-guard.md).

## უსაფრთხოება და კონტროლი

**გასაღებები.** API გასაღებები და ტოკენები მხოლოდ `.env` ფაილში ჩაწერე. ის git-ში არ ხვდება, Claude კი მას ვერც კითხულობს და ვერც წერს. როგორ შექმნა, `.env.example`-ში წერია: დააკოპირე სახელით `.env` და `PLACEHOLDER`-ის ნაცვლად ნამდვილი მნიშვნელობა ჩასვი. გასაღები ჩატში არ ჩაწერო — ასეთი შეტყობინება Claude-მდე არ მივა და გაფრთხილებას მიიღებ.

**sentinel (დარაჯი გამოტანაზე).** თუ რომელიმე ბრძანების შედეგში გასაღები გამოჩნდა, Claude მას `[REDACTED:…]`-ად ხედავს. ფარული Unicode სიმბოლოები და გარე წყაროდან მოსული „ბრძანების მსგავსი" ტექსტი ინიშნება, რომ Claude-მა ის ბრძანებად არ მიიღოს.

**observatory (დაკვირვება).** `/observatory` ქართულად გიჩვენებს, რა გააკეთეს აგენტებმა: რომელი ფაილები შეიცვალა, რომელი ბრძანება წერდა git-ში, აყენებდა, შლიდა ან ქსელში გადიოდა, რა უარყო guard-მა, რამდენი ტოკენი დაიხარჯა. `/session-close` ამის ერთ ხაზს სესიის ეპიზოდში ინახავს.

## რა ჯერ არ არის

ძრავა მუშაობს, მაგრამ ზოგი ნაწილი ჯერ მხოლოდ ქაღალდზეა — ეს გულწრფელად უნდა იცოდე. ბრძანებები Windows-ისთვისაა (`py -3.12`, Git Bash); macOS-ზე და Linux-ზე ჯერ არ შემოწმებულა. ორკესტრაციის I ეტაპი (Sonnet წერს, Opus ამოწმებს) და დისპეჩერი (decision model, რომელიც მოდელს გვირჩევს) გადაწყვეტილებად ჩაწერილია (ADR-0005, ADR-0009), კოდი კი ჯერ დასაწერია — ამიტომ ორივე გამორთულია. კოდის lint-ი, ტესტები და evals (კარიბჭეების 1–3 დონეები) ჩაირთვება მაშინ, როცა შენი პროექტის სტეკი (ტექნოლოგიები) გადაწყდება; ცალკე სახელმძღვანელოები პროექტის ტიპის მიხედვით (საიტი, თამაში, აგენტი, ავტომატიზაცია) ძრავის შემდეგ ვერსიაში მოვა. ეს ყველაფერი შენს გადასაწყვეტად წინადადებებშიც წერია ([memory/PROPOSALS.md](memory/PROPOSALS.md)).
