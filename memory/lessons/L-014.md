# L-014 — The guard over-blocks commands that merely name a trigger string

**What happened.** A commit message or `cat`-heredoc containing a PowerShell env-read phrase or a hook-skip flag, a
`grep` whose pattern names a secret file, or a `cat` or a `for` loop that merely names the approvals ledger or `approve.py` among other files is refused
(S1/B1/B2/B4) though it reads and changes nothing — the guard scans text and cannot tell a command from a description.
Hit three times 2026-10-07/09 and five more 2026-10-11 — the last a `git add` that named the approval
script. Again 2026-11-08: a `grep` that only counted a secret file's name in a
listing (B4). The engine author's own global destructive-blocker (outside this project) also reacts to the mere text of a
force-push, `rm` or `rmtree` in a command.

**What works.** The Grep/Edit tools instead of shell `grep`/heredoc; such text in a `cat <<EOF` body; rewording to
describe the string rather than type it; `git add -u`; a commit message passed as a file (`git commit -F`). That file
goes into the session's scratchpad directory (named in the system prompt), never into `.git/`: Claude Code protects
`.git/`, so every write there opens a permission window (four in one journey, 2026-10-16). A message that names no
trigger simply goes with `-m`.

**Guard.** None — documented in the over-block list of [[ADR-0007-ai-security-and-observability]]; the guard is
fail-closed by design.

The rule is this lesson's line in [[LESSONS]].
