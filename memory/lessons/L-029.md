# L-029 — A reader of project text is tried on hard inputs before it ships

**What happened.** The graph's code layer (ADR-0018 §4) gave the graph readers for every code file of a project — files the engine does not
write and cannot vouch for. Before the commit, probes fed them hard inputs, and six of them broke. A Python path
expression 2,000 levels deep ran out of Python's stack in the reader's own recursion; one 20,000 deep made `ast` stop
building the tree (RecursionError); a power chain of 20,000 overflowed the parser's stack (MemoryError) — each of the
three stopped the whole graph build, not just that file. A JavaScript line of 60,000 word characters took ~13 s (the word
before each quote was searched from every position of the run), TypeScript with 6,000 export lines and no semicolon or
quote ~6 s (20,000 lines: 88 s — each line's search for `from` read on to the file's end), and an HTML page of 40,000
comments 7 s (each comment's line was counted from the page's start).

**A second trap, in the drill itself.** The first drill inputs for the slow cases ended with an `export … from`. The
old regex's very first search then found that closing `from` and covered all 6,000 lines in one pass, so the slow path
never ran and two mutants that restore the old regex survived (M57, M58). Moving the closing match before the repeated
lines made every search fail and the mutants die.

**How we know the rule is right.** The probes' numbers were measured before the code layer went in (2026-11-10); after the fixes each
input is read in milliseconds and a file too deep is counted as unread; the mutation pass broke the layer 60 ways and
every one was caught.

**What to do.** Before a reader of project text ships, run it on nesting deeper than Python's stack (~1,000) and than
the parser holds (~3,000 and ~6,000), one long run of a single character class, thousands of repeated statement heads,
and thousands of one construct in one file. Catch RecursionError and MemoryError around `ast.parse` and around the
reader's own recursion, and count such a file as unread. A slow-input case leaves no closing match after the repeated
part, or the old code finishes in one pass and its mutant survives.

**Guard.** The drill (`graph`): the code layer's hard-input cases. A new reader: none.

The rule is this lesson's line in [[LESSONS]].
