ანალოგია: წარმოიდგინე სამშენებლო ბრიგადის ბრიგადირი, რომელსაც ყოველ დილით მეხსიერება ეშლება. რომ მუშაობა გაგრძელდეს, მაგიდაზე უნდა ედოს: დღევანდელი დავალება (სამუშაო მეხსიერება), სამუშაო ჟურნალი (ეპიზოდური), პროექტის ნახაზები და შეთანხმებები (სემანტიკური), ინსტრუქციები „როგორ ვაკეთებთ" (პროცედურული), იდეების ყუთი (პერსპექტიული) და „რა არ უნდა გავიმეოროთ" (რეფლექსიური). ქვემოთ ზუსტად ესაა — და ისიც, ვინ წერს და როდის კითხულობს აგენტი. გადაწყვეტილება: [[ADR-0002-memory-layers-and-session-distribution]].

## წესები

1. ფაქტი ერთ ადგილას ცხოვრობს; სხვაგან — ბმული. დომენის ფაქტი → `docs/domain/`, გადაწყვეტილება → ADR, მდგომარეობა → [[progress]].
2. ისტორია მხოლოდ ემატება: სხვა სესიის ეპიზოდს, ჟურნალის ძველ ჩანაწერებს და [[approvals]]-ს არავინ გადაწერს (guard G1–G3).
3. [[LESSONS]] მოკლეა და ყოველ სესიაში იტვირთება — ამიტომ მხოლოდ განმეორებადი, დადასტურებული გაკვეთილი, და ყოველს აწერია, რომელი მანქანური შემოწმება იცავს მას (ან რომ არცერთი). წესი მხოლოდ ინდექსის ხაზშია; რა მოხდა და საიდან ვიცით, რომ წესი მართალია — გაკვეთილის საკუთარ ფაილში.
4. წინადადება არ არის გადაწყვეტილება: [[PROPOSALS]]-დან არაფერი სრულდება მფლობელის „კის" გარეშე.
5. „ახლა", მიმდინარე ფაზა და „ახლა / შემდეგი" დაფებია, არა ისტორია: თითოს საკუთარი ზღვარი აქვს (`BLOCK_CAPS`, `.claude/hooks/episodic.py`), რომ სესიის დასაწყისის ბრიფი არასდროს გაიჭრას; ამბავი სესიების ჟურნალში, ეპიზოდებსა და დასრულებულ სიებშია.
