# ADR-0015: ნებართვის ფანჯარა მხოლოდ იქ, სადაც ადამიანს გადაწყვეტა შეუძლია

## კონტექსტი

ძრავის ავტორმა 2026-11-06-ს თქვა: „ძალიან ბევრ თანხმობის ფანჯარას აგდებს და ძრავას ვინც გაუშვებს, კოდს ვერ კითხულობს, და აზრი არ აქვს მაგ ბრძანებებზე". ეს გაზომილია: ძრავის ერთ სესიაში ნებართვის 203 ფანჯრიდან 203-ვე დადასტურდა და 192 მათგანი ძრავის ფაილის რედაქტირება იყო (2026-10-12); Anthropic-ის auto-რეჟიმის მონაცემით ადამიანი ფანჯრების 93%-ს ისედაც „კი"-ს ეუბნება ([[ADR-0014-harness-hardening]]-ის კონტექსტი). ფანჯარა, რომლის შინაარსიც ადამიანს არ ესმის — ფაილის გზა და diff —, კედელი არ არის: ის ადამიანს ასწავლის, რომ ყველაფერს „კი" უთხრას, მათ შორის იმ იშვიათ ფანჯრებსაც, რომლებიც მართლა მნიშვნელოვანია.

[[ADR-0014-harness-hardening]]-ის 1-ლმა პუნქტმა სწორედ ასეთი ფანჯარა დაამატა კარიბჭის ფაილებზე (`tools/gates/**`), რადგან „დრილი თავის თავს ვერ იცავს". ძრავის ფაილებზე ask-წესები (`.claude/hooks/**`, `.githooks/**`, `tools/approve.py`, `tools/gates/**`, `.claude/skills/**`, `.claude/agents/**`, `.claude/rules/**`) სრული საკეტიც არ იყო: Bash-ის ბრძანებას (მაგ. Python-ის ერთხაზიან სკრიპტს) Edit/Write-ის წესი არ ეხება — ნამდვილ საზღვრად Anthropic-ის დოკუმენტაცია sandbox-ს ასახელებს ([[ADR-0014-harness-hardening]]-ის კონტექსტი); guard-ი ([[ADR-0004-harness-permissions-hooks-guard]]) Bash-ში მხოლოდ ცნობილ საშიშ ფორმებს იჭერს. ძრავის ავტორმა სამი გზიდან აირჩია „მხოლოდ გასაგებზე": ფანჯარა რჩება იქ, სადაც ადამიანს გადაწყვეტა შეუძლია, ძრავის ფაილებს კი მანქანური შემოწმება იცავს.

## გადაწყვეტილება

1. **ფანჯარა რჩება იქ, სადაც ადამიანს გადაწყვეტა შეუძლია.** ask-სიაში რჩება: პროგრამის დაყენება (pip, npm, uv, npx, winget, choco, brew, sudo, apt, dnf); ცვლილების გაგზავნა და ისტორია (git push, merge, rebase, reset, `commit --amend`, restore, `checkout --`, stash, `branch -d` და `git config` — მათ შორის `core.hooksPath`, commit-ის შემოწმების გამორთვის გზა); წაშლა (rm, rmdir, git rm); ფასიანი გაშვება (ორკესტრაციის ციკლები, დისპეჩერი, codex) და MCP-ის ხელსაწყოები; ფულისა და ჩართვის გადამრთველები (`orchestration/config.toml`). თითოეული ერთი წინადადებით აიხსნება — „დავაყენო X?", „გავგზავნო GitHub-ზე?", „წავშალო Y?", „დავხარჯო რამდენიმე ცენტი?" —, და ფანჯრამდე აგენტი ამ წინადადებას ქართულად წერს.
2. **ძრავის ფაილებზე ფანჯარა ქრება** — სახელოსნოშიც და ნაკრებშიც: `Edit`/`Write`-ის ask-წესები `.claude/hooks/**`, `.githooks/**`, `tools/approve.py`, `tools/gates/**`, `.claude/skills/**`, `.claude/agents/**`, `.claude/rules/**`-ზე (14 წესი) ამოიღება. ორივე სია ერთნაირი ხდება. AGENTS.md-ის საზღვარი უცვლელია: harness-ის ფაილი მხოლოდ იმ დავალებისთვის იცვლება, რომელიც ადამიანმა ითხოვა; ქრება მხოლოდ თითო რედაქტირების ფანჯარა.
3. **გამონაკლისი — თავად ნებართვების ფაილი.** `.claude/settings.json` და `.claude/settings.local.json` ask-ს ინარჩუნებს: ამ ფაილის ერთი ცვლილება ყველა სხვა წესს და guard-ის hook-ს ერთბაშად ხსნის და მაშინვე მოქმედებს, commit-მდე. ესეც ერთი წინადადებით აიხსნება: „აგენტს საკუთარი წესების შეცვლა უნდა".
4. **ფანჯრის ნაცვლად — მანქანა.**
   - **commit-ზე დრილი** (უკვე არის): ძრავის ფაილის ყოველ ცვლილებაზე სრული დრილი ეშვება (`HARNESS_PREFIXES`); გამორთული gate ან ამოღებული guard-ის წესი commit-ს აწითლებს, რადგან მისი ჩადებული შემთხვევა DEAD ხდება.
   - **დრილის იატაკი** (ახალი): ARMED-ების რაოდენობა ratchet-ია (მხოლოდ ზემოთ მოძრავი ზღვარი) — commit, რომლის დრილიც ჩაწერილ იატაკზე ნაკლებ შემთხვევას აიარაღებს, წითელია; იატაკი დრილთან ერთად იზრდება, დაწევა კი მხოლოდ მფლობელის `/approve`-ით შეიძლება, ბაიტების ბიუჯეტის მსგავსად. ასე ADR-0014-ის მიზეზი — „დრილი თავის თავს ვერ იცავს" — ფანჯრის ნაცვლად მანქანით იხურება.
   - **სესიის ბოლოს ერთი ქართული ხაზი** (ახალი): რომელი ძრავის ფაილები შეიცვალა ამ სესიაში, ჩვეულებრივი სიტყვებით („guard — უსაფრთხოების შემმოწმებელი", „კარიბჭეების სია"), და გაიარა თუ არა მათმა commit-მა დრილი; guard-ისა და commit-ის შემოწმების (`.githooks/`) ცვლილებას ⚠ აქვს. ეს ინფორმაციაა და არა საკეტი: ადამიანი ხედავს, რომ რაღაც შეიცვალა, და შეუძლია ჰკითხოს, რატომ.
5. **ADR-0014-ის 2–5 პუნქტები უცვლელად გადმოდის** და უკვე აშენებულია (2026-11-01): ჩავარდნილი guard-ი ბლოკავს (`onFailure: block`, GUARD[X1]/[X2]); sandbox-ი ჩართულია, სადაც არსებობს, და მისი მდგომარეობა ყველგან ჩანს (ნაგულისხმევი ჩართვა — ცოცხალი ცდის შემდეგ); auto-რეჟიმი რჩება, საზღვარი სიებია; მთლიანობის მანიფესტი ცალკე წინადადებაა. ამიტომ ეს ADR ADR-0014-ს მთლიანად ანაცვლებს (`supersedes`), რომ ერთი ნაბიჯი ერთ ტექსტში ეწეროს (L-018).
6. **აშენება — მხოლოდ `/approve adr 0015`-ის შემდეგ**, თითო ცვლილება ცალკე commit-ით, დრილითა და მუტაციით: ორივე ask-სია (სახელოსნო და ნაკრები); დრილის `wiring` ჯგუფი; დრილის იატაკი; სესიის ბოლოს ხაზი; `tools/gates/README.md`-ისა და AGENTS.md-ის ფორმულირება; ნებართვის ცოცხალი ზონდი.

## განხილული ალტერნატივები

- **დარჩეს, როგორც არის.** უარყოფილია: 203-დან 203 დადასტურება; ფანჯარა, რომელსაც ადამიანი ვერ კითხულობს, რიტუალია და მნიშვნელოვან ფანჯრებსაც აუფასურებს.
- **ფანჯარა guard-ში გადავიდეს — სტუდენტის პროექტში იკითხოს, სახელოსნოში არა.** ძრავის ავტორმა 2026-11-06-ს სხვა გზა აირჩია: სტუდენტის პროექტშიც ფანჯარა ისეთივე გაუგებარია — სტუდენტიც კოდს ვერ კითხულობს.
- **deny ძრავის ფაილებზე სტუდენტის პროექტში.** უფრო ძლიერია, მაგრამ ასლში ძრავის განახლებას (ნაკრებიდან ფაილების გადატანას) აგენტის ხელით შეუძლებელს ხდის; ახლა არა — შეიძლება ცალკე წინადადებად, თუ ცდა აჩვენებს, რომ განახლება git-ით მარტივია.
- **ნებართვების ფაილის ფანჯარაც მოიხსნას.** უარყოფილია: ეს ერთადერთი ფაილია, რომლის ცვლილებაც ყველა სხვა დაცვას ერთბაშად და მაშინვე ხსნის; ფანჯარა იშვიათია და ერთი წინადადებით აიხსნება.

## შედეგები

**+** ძრავის სესიაში ფანჯრების დიდი ნაწილი ქრება (გაზომვით 203-დან 192); დარჩენილი იშვიათია და გასაგები, ამიტომ ადამიანი მათ მართლა კითხულობს. სახელოსნოსა და ნაკრების სიები ერთნაირია — სინქრონი მარტივდება. ADR-0014-ის მიზეზი მანქანით იხურება და არა ფანჯრით.

**−** სესიის შიგნით ძრავის ფაილი (მაგ. guard) ფანჯრის გარეშე იცვლება და ცვლილება მაშინვე მოქმედებს: ის commit-ზე (დრილი, იატაკი) და სესიის ბოლოს (ხაზი) ჩანს, მაგრამ commit-მდე არ ჩერდება. საიდუმლო ფაილების deny-წესები ნებართვების ფაილშია, რომელიც ფანჯრით რჩება დაცული, ამიტომ ისინი guard-ის ცვლილების შემდეგაც მოქმედებს; git ყოველ ცვლილებას ინახავს და აბრუნებს; ნაკრებში PR-ის CI კარიბჭეებს თავიდან უშვებს. სუსტი წერტილი, რომელიც პირდაპირ უნდა ითქვას: `.githooks/pre-commit`-ის შეცვლით commit-ის შემოწმება შეიძლება გაითიშოს, და ამას დრილი ვერ დაიჭერს, რადგან დრილს სწორედ ის უშვებს — აქ მოწმეები სესიის ბოლოს ⚠-ხაზი და ნაკრების CI-ია. ორი ახალი მანქანური შემოწმება (იატაკი და ხაზი) ერთ აშენების სესიას მოითხოვს, თითოს დრილითა და მუტაციით.

## დადასტურება

- დრილი, `wiring` ჯგუფი: ძრავის ფაილებზე ask აღარ არის; ნებართვების ფაილზე, `orchestration/config.toml`-ზე, დაყენებაზე, push/merge-ზე, წაშლასა და ფასიან გაშვებებზე — არის; მუტანტი (ნებართვების ფაილის წესი ამოღებული) → DEAD.
- დრილის იატაკი: დრილიდან ამოღებული ერთი შემთხვევა → commit წითელი; იატაკის დაწევა მფლობელის ჩანაწერის გარეშე → LEDGER; მუტანტები → DEAD.
- სესიის ბოლოს ხაზი: guard-ის ცვლილება → ხაზი ⚠-ით; ძრავის ფაილის ცვლილების გარეშე → ხაზი არ ჩნდება.
- ნებართვის ცოცხალი ზონდი სუფთა ასლში (`--setting-sources project,local`): ძრავის ფაილის რედაქტირება ფანჯრის გარეშე გადის; `git push`, დაყენება და `settings.json`-ის რედაქტირება ფანჯარას ხსნის; მუტანტი ნებართვების ფაილის წესის გარეშე — გადის.
- შემდეგ ძრავის სესიაში ფანჯრების რაოდენობა `/observatory`-ით: მხოლოდ 1-ლი და მე-3 პუნქტის ქმედებები.
