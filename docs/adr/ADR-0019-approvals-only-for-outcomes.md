# ADR-0019: ადამიანი ამტკიცებს მიზანს და ოთხ შედეგს — დანარჩენს მანქანური შემოწმება აჩერებს

## კონტექსტი

ძრავის ავტორმა 2026-11-08-ს დაწერა: „ამდენი approves უნდა მოვხსნათ და მაქსიმალურად მყარი, მანქანური შემოწმებები, ქვეაგენტები სისტემა ავწყოთ, მაინც ვერ გაარჩევენ არაკოდერები" (მართლწერა გასწორებულია). [[ADR-0015-permission-windows-only-where-a-person-decides]]-მა ეს პრობლემა ნებართვის ფანჯრებში უკვე გადაჭრა: ფანჯარა, რომლის შინაარსიც ადამიანს არ ესმის, კედელი არ არის — ძრავის ერთ სესიაში 203-დან 203 ფანჯარა დადასტურდა —, და ასეთი ფანჯარა ადამიანს ყველაფერზე „კი"-ს თქმას ასწავლის. დოკუმენტების დამტკიცებაზეც იგივე ხდება. ახალ პროექტში ადამიანი პირველ მუშა ვერსიამდე ოთხჯერ ამტკიცებს — განზრახვას (`/approve intent`), სპეციფიკაციას, სტეკის ADR-ს და გეგმას (`tools/context_graph.py`-ის `project_stage` მე-2–4 ეტაპებზე სწორედ ამ სტატუსებს ელოდება) —, მერე კი მეხუთედ, გაშვებას (`/approve live N`). ამ ოთხიდან ორს — სტეკის ADR-ს და გეგმას — კოდის არმცოდნე ვერ შეაფასებს, სპეციფიკაციას კი მხოლოდ ნაწილობრივ: მათი დამტკიცება ისეთივე რიტუალი ხდება, როგორიც გაუგებარი ფანჯარა.

ავტორის მეორე იდეა — დამტკიცების ნაცვლად ქვეაგენტები (subagent) — სიმართლის ნახევარია. ქვეაგენტის მიმოხილვა (spec-reviewer, სამი კრიტიკოსი, refuter) ენობრივი მოდელის შეფასებაა: იგივე მოდელი იგივე ინსტრუქციით იმავე ადგილას ვერ ხედავს, და მისი „approve" ვერ განსხვავდება მიმომხილველისგან, რომელსაც არაფერი შეუმოწმებია. ძრავის წესით მტკიცებულება მხოლოდ მანქანური შემოწმებაა, რომელიც დრილში განზრახ გატეხეს და მან ეს დაიჭირა (AGENTS.md: „let a machine check prove it — assurance is not evidence"). იგივე დასკვნა აქვს აგენტის ციკლებზე ძრავის აშენებისას ჩატარებულ კვლევას (2026 წლის ნოემბერი): აგენტის ციკლის პირველი ნაწილი შემოწმებაა, რომელსაც აგენტი ვერ ცვლის. აგენტი იმავე დღეს ავტორს ნაწილობრივ დაეთანხმა: კოდის დონის ფანჯრები უნდა გაქრეს, ოთხი შედეგის დამტკიცება — გამოქვეყნება, ფულის ხარჯვა, წაშლა და გაშვება — დარჩეს, ქვეაგენტი კი კედელი ვერ იქნება; ჯერ ADR. ეს ADR სწორედ ის წინადადებაა.

## გადაწყვეტილება

1. **ადამიანი ამტკიცებს მიზანს და ოთხ შედეგს — და მეტს არაფერს.** თითოეული ერთი ქართული წინადადებით იკითხება: რა მოხდება, რა ღირს და შეიძლება თუ არა დაბრუნება.
   - **მიზანი** — `intent.md`, ინტერვიუს ბოლოს (`/approve intent`), ერთხელ პროექტზე და მიზნის ყოველ ცვლილებაზე. ეს ერთადერთი დოკუმენტია, რომლის დამტკიცებაც რჩება: მასში ადამიანის საკუთარი სიტყვებია და ის მას ბოლომდე ესმის; მანქანური შემოწმებები ყველაფერს მასთან ზომავს, დამტკიცებული განზრახვა კი გაყინულია — აგენტი მას ჩუმად ვერ შეცვლის (guard; ცვლილება ხელახლა დამტკიცებას ითხოვს).
   - **გამოქვეყნება** — ყველაფერი, რაც ამ კომპიუტერს ტოვებს: `git push`, PR-ის შერწყმა, deploy, წერილის, შეტყობინების ან პოსტის გაგზავნა, MCP-ის ყოველი ხელსაწყო (მისი მოთხოვნა გარე სერვისს მიდის).
   - **ფულის ხარჯვა** — ყოველი ფასიანი გაშვება, თავად საუბრის გარდა: ორკესტრაციის ციკლები, დისპეჩერი, codex, ფასიანი API, სერვისი ან გამოწერა, და გადამრთველები, რომლებიც მათ რთავს (`orchestration/config.toml`); ყოველთვის რიცხვით — რამდენი და რა ზღვრით.
   - **წაშლა** — ყველაფერი, რაც სამუშაოს, ისტორიას ან მონაცემს აქრობს: `rm`, `rmdir`, `git rm`, `reset`, `rebase`, `commit --amend`, `restore`, `checkout --`, `stash`, `branch -d`, მონაცემის წამშლელი მიგრაცია, ღრუბლოვანი რესურსის წაშლა.
   - **გაშვება** — `/approve live N`, როცა ადამიანმა პროდუქტი მუშაობაში ნახა (მე-5 ეტაპიდან მე-6-ზე, [[ADR-0013-sdlc-loop-2026-upgrade]]).

   ამათ გარდა რჩება ორი საზღვარი, რომლებიც შედეგი არ არის: (ა) პროექტის საქაღალდის გარეთ არაფერი იცვლება კითხვის გარეშე — გლობალური დაყენება (winget, choco, brew, sudo, apt, dnf, `npm -g`, `pip` პროექტის `.venv`-ის გარეთ) იკითხება: „დავაყენო X შენს კომპიუტერზე?"; (ბ) აგენტი საკუთარ წესებს კითხვის გარეშე არ ცვლის — ნებართვების ფაილი (`.claude/settings.json`, `.claude/settings.local.json`) და რეპოზიტორიის პარამეტრები (`git config`, მათ შორის `core.hooksPath` — commit-ის შემოწმების გამორთვის გზა).

2. **სპეციფიკაცია, გეგმა და პროექტის ADR აგენტისაა — მანქანური შემოწმების უკან.** ჩნდება ახალი სტატუსი `checked`: მას აგენტი წერს და ის ნიშნავს „ამ დოკუმენტის მანქანური შემოწმებები ამ commit-ზე გადის". `graph` gate ყოველ commit-ზე თავიდან ითვლის, მართლა გადის თუ არა ყოველი `checked` დოკუმენტი, და რომელიც ვერ გადის, commit-ს აწითლებს. ეტაპების გამტარი ([[ADR-0011-idea-first-stage-conductor]]) მე-2–4 ეტაპებს `checked`-ზე ამოძრავებს; მფლობელის `approved` / `accepted` ისევ შესაძლებელია, მაგრამ აღარ არის საჭირო. შემოწმებები:
   - **სპეციფიკაცია** — ყოველი მოთხოვნა განზრახვის მიზანს (G-ს) უკავშირდება; ყოველ მიღების კრიტერიუმს თავისი ტესტი ან eval აქვს (§6, [[ADR-0013-sdlc-loop-2026-upgrade]]); ღია კითხვა არ რჩება; spec-reviewer-ის შენიშვნები ფაილშია, `tools/check_findings.py`-ს გადის და ყოველ critical / high შენიშვნას პასუხი აქვს; პირველი ნაწილი ერთი ეკრანია ჩვეულებრივი სიტყვებით — რას გააკეთებს, როგორ გავიგებთ, რომ მზადაა, რა ეღირება და რა გამოქვეყნდება.
   - **გეგმა** — ყოველი ამოცანა სპეციფიკაციის მოთხოვნას ან კრიტერიუმს უკავშირდება და თავის შემოწმებას ასახელებს; დაბრუნების გზა წერია.
   - **პროექტის ADR** — ორი ალტერნატივა მაინც, სახელმძღვანელოს ხუთი ბრძანება (install · run · lint · test · show), მანქანური „დადასტურება" და ფულისა და გამოქვეყნების შედეგები ჩვეულებრივი სიტყვებით — ისინი მერე 1-ლი პუნქტის კითხვებად ჩნდება, როცა დადგება.

   ერთეკრანიან შეჯამებას აგენტი ადამიანს აჩვენებს — ინფორმაციად და არა კითხვად: „გაჩერდი" ნებისმიერ დროს შეიძლება, და დოკუმენტი მაშინ `draft`-ზე ბრუნდება. ძრავის ADR-ები (`scope: engine`) მფლობელის `/approve adr`-ით რჩება: ისინი თავად შემოწმებების წესებს ცვლის, აგენტი კი საკუთარ წესებს ადამიანის გარეშე არ ცვლის (1-ლი პუნქტის „ბ").

3. **ქვეაგენტი გვირჩევს, მანქანა აჩერებს.** ქვეაგენტის მიმოხილვა — spec-reviewer, კრიტიკოსები, refuter, ორკესტრაციის checker ([[ADR-0005-maker-checker-orchestration]]) — არასდროს არის ბარიერი: არც „მზადაა"-სთვის და არც `checked`-ისთვის. მისი შედეგი მანქანით მოწმდება — შენიშვნა ადგილით, ციტატითა და სიმძიმით (`tools/check_findings.py`), checker-ის `FINDING` / `PREVIOUS` / `VERDICT` ხაზები (ნამდვილი მოდელით შემოწმდა 2026-11-09) —, და high შენიშვნას პასუხი სჭირდება, მაგრამ სუფთა მიმოხილვა თავისთავად არაფერს ამტკიცებს. ბარიერი ის შემოწმებაა, რომელსაც აგენტი იმავე commit-ში ჩუმად ვერ შეცვლის: gate-ები, დრილი და მისი იატაკი (მხოლოდ ზემოთ მოძრავი ზღვარი) და მფლობელის ჟურნალი (LEDGER).

4. **ნებართვის ფანჯრები = ოთხი შედეგი და ორი საზღვარი.** ADR-0015-ის ask-სია ამ ექვს ჯგუფად ლაგდება; ერთი რამ იცვლება და ერთი ემატება:
   - **იცვლება:** პროექტის საქაღალდეში დაყენება (`.venv`, `node_modules`) ფანჯრის გარეშე გადის, თუ დამოკიდებულება პროექტის სახელმძღვანელოს სიაშია (მას ძრავის ავტორი ამოწმებს), lockfile-ში ზუსტი ვერსიითაა ჩაწერილი და `deps-audit` gate-ი ცნობილ მოწყვლადობას ვერ პოულობს; აუდიტის ხელსაწყო თუ არ არის, შედეგი INCONCLUSIVE-ია, და ის აჩერებს, არ უშვებს. სიის გარეშე დამოკიდებულება ფანჯრით რჩება, წინადადებით „X ძრავის შემოწმებულ სიაში არ არის".
   - **ემატება:** სესიის დაწყების ბრიფი ამოწმებს, რომ commit-ის შემოწმებები ჩართულია (`core.hooksPath` = `.githooks`), და სხვა მნიშვნელობაზე ⚠-ხაზს წერს. ADR-0015-ის მიერ დასახელებული სუსტი წერტილი — „commit-ის შემოწმება შეიძლება გაითიშოს" — ასე ერთ-ერთი გზით მანქანით ჩანს; `.githooks/pre-commit`-ის შიგთავსის ცვლილებას ისევ სესიის ბოლოს ⚠-ხაზი და ნაკრების CI ხედავს.

5. **რიგი: არცერთი ფანჯარა და არცერთი დამტკიცება არ ქრება, სანამ მისი შემცვლელი შემოწმება დრილში ARMED არ არის.** აშენება — მხოლოდ `/approve adr 0019`-ის შემდეგ, თითო ცვლილება ცალკე commit-ით, დრილითა და მუტაციით: (ა) `checked` სტატუსი, მისი შემოწმება `graph` gate-ში, ეტაპების გამტარი და guard; (ბ) `/spec`, `/feature-plan`, `/adr`, სახელმძღვანელოები, AGENTS.md, CLAUDE.md, `process.md` და `REVIEW.md` — ერთ commit-ში, რომ ერთი ნაბიჯი ყველგან ერთნაირად ეწეროს (L-018); (გ) ბრიფის `core.hooksPath`-ის ხაზი; (დ) სახელმძღვანელოების დამოკიდებულებების სია, `deps-audit` gate და ask-სიის ცვლილება — ამ თანმიმდევრობით; ნაკრებში — აშენების შემდეგ, ცალკე PR-ით.

6. **ADR-0015-ის 2–5 პუნქტები უცვლელად გადმოდის** და უკვე აშენებულია: ძრავის ფაილებზე ფანჯარა არ არის; ნებართვების ფაილი ფანჯარას ინარჩუნებს; commit-ზე დრილი, დრილის იატაკი და სესიის ბოლოს ძრავის ფაილების ხაზი; [[ADR-0014-harness-hardening]]-ის 2–5 პუნქტები. ამიტომ ეს ADR ADR-0015-ს მთლიანად ანაცვლებს (`supersedes`), რომ ერთი ნაბიჯი ერთ ტექსტში ეწეროს (L-018). [[ADR-0013-sdlc-loop-2026-upgrade]]-ის გადაწყვეტილება — evals სპეციფიკაციასთან და მე-6 ეტაპი — უცვლელია; იცვლება მხოლოდ ის, ვინ ამოძრავებს მე-2–4 ეტაპებს. [[ADR-0001-foundation-and-sdlc-loop]]-ის ციკლის ჩამონათვალი (ის ჯერ `proposed`-ია) ამ ADR-ის დამტკიცებისას განახლდება.

## განხილული ალტერნატივები

- **დარჩეს, როგორც არის** (ADR-0015 და დოკუმენტების ყველა დამტკიცება). უარყოფილია: პირველ მუშა ვერსიამდე ოთხი დამტკიცება, რომელთაგან ორს ადამიანი ვერ შეაფასებს — იგივე რიტუალი, რაც ADR-0015-მა ფანჯრებში გაზომა.
- **მკაცრად ოთხი — მიზანიც აღარ მტკიცდება.** უარყოფილია: მანქანური შემოწმებები ყველაფერს მიზანთან ზომავს; დაუმტკიცებელი მიზანი გაყინული არ არის, ამიტომ აგენტს მისი გადაწერა შეეძლება, და ყოველი კავშირი მაინც გაივლიდა. თანაც ეს ერთადერთი დოკუმენტია, რომელიც ადამიანს ბოლომდე ესმის, და მისი დამტკიცება პროექტზე ერთი შეტყობინება ჯდება.
- **ერთი დამტკიცება ფუნქციაზე** — სპეციფიკაცია, ADR და გეგმა ერთ შეჯამებაში, ერთი `/approve`-ით. ყველაზე ახლო ალტერნატივაა, მაგრამ არ ავირჩიეთ: დამტკიცებებს სამჯერ ამცირებს, თუმცა ყოველ ფუნქციაზე ადამიანს ისევ ტექნიკურ შეკვრას უდებს წინ. ის სათადარიგოდ რჩება, თუ პილოტმა აჩვენა, რომ აგენტი სპეციფიკაციაში ხშირად ცდება — ეს იზომება: რამდენ ნაჩვენებ ვერსიას სჭირდება ცვლილება მე-5 ეტაპზე.
- **ქვეაგენტი კედლად** (ავტორის იდეის პირდაპირი წაკითხვა — მიმომხილველის `approve` ადამიანის დამტკიცებას ანაცვლებს). უარყოფილია: ენობრივი მოდელის მიმოხილვის დრილი ვერ დაამტკიცებს, რომ ის ყოველ ჯერზე დაიჭერს; იგივე მოდელს maker-ის ბრმა წერტილი აქვს. მიმოხილვა რჩება რჩევად, რომლის შედეგიც მანქანით მოწმდება (მე-3 პუნქტი).

## შედეგები

**+** ახალ პროექტში ადამიანის დამტკიცებები პირველ მუშა ვერსიამდე ოთხიდან ერთამდე მცირდება (განზრახვა), მერე — გაშვება და ის კითხვები, რომლებიც მართლა დადგება (გამოქვეყნება, ფული, წაშლა). ყოველი დარჩენილი კითხვა ერთი წინადადებაა, რომელსაც ადამიანი თავად აფასებს. მანქანური შემოწმებები ძლიერდება: `checked`-ის ხელახალი შემოწმება ყოველ commit-ზე, `core.hooksPath`-ის ხაზი, `deps-audit`. ფანჯრებსა და დოკუმენტებს ერთი წესი აქვს — ადამიანი ამტკიცებს შედეგს და არა მექანიზმს.

**−** ადამიანი აღარ აჩერებს არასწორად გაგებულ სპეციფიკაციას აშენებამდე — ის მას ერთეკრანიან შეჯამებაში და მე-5 ეტაპზე ხედავს, და ასეთი შეცდომა ხელახლა აშენება ჯდება. `checked` ზუსტად იმდენად კარგია, რამდენადაც მისი შემოწმებები: კავშირი ამტკიცებს, რომ მოთხოვნა მიზანს უკავშირდება, და არა იმას, რომ ის სწორია — ამას მანქანა ვერ წყვეტს. აშენება რამდენიმე სესიაა: ახალი სტატუსი, gate, ეტაპის წესი, guard, skill-ები, სახელმძღვანელოები, დამოკიდებულებების სია, დრილი და ნაკრების PR. ძრავის ADR-ები ისევ ძრავის ავტორს სჭირდება — სახელოსნოში დღეს ცხრა ელოდება, ეს მეათეა. `deps-audit`-ს ხელსაწყო სჭირდება (`pip-audit`, `npm audit`); მის ჩართვამდე პროექტში დაყენება ფანჯრით რჩება.

## დადასტურება

- დრილი, `wiring` ჯგუფი: ask-სიაში მხოლოდ ოთხი შედეგი და ორი საზღვარია; სახელმძღვანელოს სიის დამოკიდებულება ფანჯრის გარეშე გადის, სიის გარეშე — ფანჯრით; მუტანტები (წესი ამოღებული ან დამატებული) → DEAD.
- დრილი, `graph` ჯგუფი: `checked` სპეციფიკაცია მოთხოვნით, რომელიც მიზანს არ უკავშირდება → წითელი; კრიტერიუმი ტესტისა და eval-ის გარეშე → წითელი; უპასუხო high შენიშვნა → წითელი; სუფთა კონტროლი → მწვანე; აგენტის `approved` ისევ guard-ის G4-სა და LEDGER-ზე ჩერდება; მუტანტები → DEAD.
- ეტაპების გამტარი: განზრახვა `accepted` და სპეციფიკაცია, ADR და გეგმა `checked` → მე-4 ეტაპი; განზრახვა დაუმტკიცებელი → 1-ლი ეტაპი, დანარჩენის მიუხედავად.
- ბრიფი: დროებით რეპოში შეცვლილი `core.hooksPath` → ⚠-ხაზი; კონტროლი → სიჩუმე; მუტანტი → DEAD.
- `deps-audit`: ცნობილი მოწყვლადობის მქონე დამოკიდებულება → წითელი; აუდიტის ხელსაწყოს გარეშე → INCONCLUSIVE; კონტროლი → მწვანე.
- ცოცხალი გზა (L-016; ფასიანია — მხოლოდ მფლობელის „კი"-თ): ნაკრების ახალი ასლი, იდეა პირველ შეტყობინებად, ნამდვილი `claude -p` სესია პირველ მუშა ვერსიამდე; ადამიანის დამტკიცებები და ფანჯრები `/observatory`-ით ითვლება — მოლოდინი: `/approve intent` და მხოლოდ ის ფანჯრები, რომლებიც 1-ლ პუნქტშია —, იმავე იდეაზე დღევანდელ რაოდენობასთან შედარებით.
