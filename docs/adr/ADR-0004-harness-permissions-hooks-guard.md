# ADR-0004: Harness — წვდომები, აკრძალვები, hook-ები და guard

## კონტექსტი

ძრავის პრინციპი ([[intent]] P4): ზუსტად უნდა განისაზღვროს, რაზე აქვს აგენტს წვდომა, რა ბრძანებების გაშვება შეუძლია და სად არის შეზღუდული. ფაქტები (გადამოწმებული 2026-09-18): მომხმარებლის გლობალურ `~/.claude/settings.json`-ს საკუთარი აკრძალვები და რეჟიმი შეიძლება ჰქონდეს (ძრავის ავტორს 115 აკრძალვა და ავტომატური რეჟიმი, `defaultMode: auto`, ჰქონდა) — ამ პროექტის წესები და guard მათ გარეშეც მუშაობს; პროექტის `defaultMode` ავტომატურ რეჟიმს ვერ ცვლის; წესების რიგი: deny → ask → allow, ხოლო `ask` წესი ავტომატურ რეჟიმშიც კითხულობს; პროექტის allow წესებს სამუშაო საქაღალდის ნდობა (workspace trust) სჭირდება, deny/ask-ს — არა; **sandbox Windows-ზე არ მუშაობს** (მხოლოდ macOS / Linux / WSL2).

## გადაწყვეტილება

**1. წესები (`.claude/settings.json`) — სამი დონე:**

- **deny (არასდროს):** საიდუმლოების წაკითხვა — Read ხელსაწყოთი (`.env`, `.env.local`, `*.pem`, `*.key`, `secrets/`, `credentials*.json`, ქვესაქაღალდეებშიც) და shell-ით (`type`, `head`, `tail`, `more`, `less`, `Get-Content` + `.env`; `cat` და სხვა ბრძანებები, რომლებიც საიდუმლოების ფაილს კითხულობს ან git-ში ამატებს, guard-ის B4 წესით ჩერდება); კარიბჭეების გვერდის ავლა (`--no-verify`, `commit -n`, `-c core.hooksPath`); force push; `approvals.md`-ის და `episodes/INDEX.md`-ის ხელით ცვლა.
- **ask (მფლობელს ეკითხება):** ყველა ფაილი, რომელიც წყვეტს, რა შეუძლია ან რა ევალება აგენტს — `.claude/settings*.json`, hooks, `.githooks/`, მთელი `tools/` (გრაფი, `approve.py`, კარიბჭეები), `.claude/skills/`, `.claude/agents/`, `.claude/rules/`, მთელი `orchestration/`, `CLAUDE.md`, `AGENTS.md`, `REVIEW.md`, `memory/LESSONS.md` (ასე თვითგანვითარება მხოლოდ მფლობელის თანხმობით ხდება მანქანურადაც, არა მხოლოდ სიტყვით); პაკეტების დაყენება (`pip`, `npm`, `uv`, `winget`); ფაილების წაშლა (`rm`, `git rm`); `git push`, `merge`, `rebase`, `reset`; ორკესტრაციის გაშვება; `git config`.
- **allow (კითხვის გარეშე):** პროექტის ინსტრუმენტები (`py -3.12 tools/…`, hooks-ის სკრიპტები), git-ის წაკითხვა და ჩვეულებრივი commit, ფაილების კითხვა.

**2. Hook-ები** (ყველა `bash .claude/hooks/py.sh …`-ით, ერთ ადგილას არჩეული Python 3.12-ით):

| მოვლენა | სკრიპტი | რას აკეთებს |
|---|---|---|
| SessionStart | `episodic.py start`, `context_graph.py brief` | სამუშაო მეხსიერება + გრაფის ბრიფი ([[ADR-0002-memory-layers-and-session-distribution]]) |
| PostCompact | `episodic.py compact` | compact-ის მრიცხველი + შეჯამება ეპიზოდში |
| SessionEnd | `episodic.py end` | ეპიზოდის დახურვა + ფონური შეჯამება |
| PreToolUse (Edit/Write/MultiEdit/NotebookEdit, Bash/PowerShell) | `guard.py` | ქვემოთ |
| Stop | `stop_gate.py` | სესიის მიერ შეცვლილ ფაილებზე სწრაფი gates; ჩავარდნა → აგენტი აგრძელებს და ასწორებს |

**3. Guard (`.claude/hooks/guard.py`)** — მფლობელის დამტკიცება და ისტორია არ უნდა გაყალბდეს: G1 `approvals.md`-ის ცვლა; G2 `episodes/INDEX.md`; G3 სხვა სესიის ეპიზოდი (მხოლოდ `needs_reconcile`/`reconciled_*`); G4 მფლობელის სტატუსის მინიჭება; G5 გაყინული დოკუმენტის ცვლა (დაშვებულია მხოლოდ „ხელახლა გახსნა", გეგმაში — მონიშვნა, გადახრის დამატება, წინ წაწევა); G6 საიდუმლოების ფაილის ჩაწერა (`.env`, `*.pem`, `*.key`, `secrets/` …; `.env.example` დოკუმენტაციაა და დაშვებულია); B1 `approve.py`-ის გაშვება ან `approvals.md`-ში ჩაწერა shell-ით; B2 კარიბჭეების გამოტოვება — `--no-verify` (მისი შემოკლება `--no-veri`-ც, რადგან git შემოკლებულ ოფციას იღებს), `commit -n`, `core.hooksPath`-ის გადაფარვა (`-c`, `--config-env`, `GIT_CONFIG_*` ცვლადები); B3 force push; B4 საიდუმლოების ფაილი ნებისმიერ ბრძანებაში, რომელსაც მისი წაკითხვა ან git-ში დამატება შეუძლია (`cat`, `Get-Content`, `python -c "open('.env')"`, `git add .env`, `cp ~/.ssh/…`). guard ბრძანებას ისე კითხულობს, როგორც shell ასრულებს: ყოველი ხაზი ცალკე ბრძანებაა; git შეფუთვის უკან (`env git …`, `xargs git …`), ჩადგმულ shell-ში (`bash -c "…"`, `pwsh -Command "…"`, `cmd /c …`) და ჩასმაში (`$(…)`, backtick-ები, `<(…)`) ისევე მოწმდება, როგორც პირდაპირ; `cat <<EOF` ტექსტი (commit-ის შეტყობინება) ბრძანებად არ ითვლება, Python-ისთვის მიწოდებული კი — ითვლება. ყოველ ბლოკს ჟურნალი (`guard.log`) აქვს.

**4. გულწრფელი საზღვარი:** guard არის **სიჩქარის ბორცვი და აუდიტის კვალი, არა საკეტი** — shell-ის მქონე აგენტი ყოველთვის იპოვის შემოვლით გზას. ამიტომ ბოლო ხაზი მანქანური შემოწმებაა: gate-ის LEDGER წესი ჩავარდება, თუ დამტკიცებულ სტატუსს ჟურნალის ჩანაწერი არ აქვს, როგორი გზითაც არ უნდა მოხვედრილიყო იქ; git-ის ისტორია კი აჩვენებს, ვინ შეცვალა.

**5. Sandbox:** ჯერ არა — Windows-ზე არ მუშაობს. თუ მომავალში სამუშაო WSL2-ში გადავა, ცალკე ADR-ით ჩაირთვება.

**6. Skill-ის `!` ინექცია** (`/approve`, `/session-close`, `/orchestrate`): გადამოწმებულია, რომ PreToolUse hook-ს არ გადის, `allowed-tools`-ით წინასწარ დაშვებას საჭიროებს და `CLAUDE_PROJECT_DIR` გარემოს ცვლადს ვერ ხედავს (მხოლოდ `${CLAUDE_PROJECT_DIR}` ჩანაცვლებას). ამიტომ `/approve` guard-ს არ ეჯახება, აგენტი კი `approve.py`-ს ვერ უშვებს. ერთი ცნობილი სისუსტე: `'$ARGUMENTS'` ბრძანების ხაზში ჩაისმება როგორც ტექსტი, ამიტომ ბრჭყალის გამრღვევი არგუმენტი (`x'; სხვა-ბრძანება; '`) თეორიულად მეორე ბრძანებას დაამატებდა. გაზომილია (2026-09-18): ასეთი შედგენილი ბრძანება ნებართვების ფენამ უარყო და არაფერი გაეშვა, რადგან `allowed-tools` მხოლოდ `approve.py`-ის ერთ გამოძახებას უშვებს. გარდა ამისა, `$ARGUMENTS`-ს მხოლოდ `/approve` იყენებს, მას კი მხოლოდ მფლობელი იძახებს (`disable-model-invocation: true`), ანუ არგუმენტს ყოველთვის მფლობელი წერს.

## განხილული ალტერნატივები

- **მხოლოდ გლობალური წესები:** პროექტის სპეციფიკა (დამტკიცება, მეხსიერება) ვერ დაიცვებოდა. უარყოფილია.
- **Guard, რომელიც ყველაფერს კრძალავს უცნობ შემთხვევაში (fail-closed):** Python-ის გაფუჭება მთელ სამუშაოს გაყინავდა. არჩეულია: ხმამაღალი შეცდომა (exit 1, ჩანს ეკრანზე), მაგრამ არა გაყინვა; ბოლო ხაზს gate იცავს.
- **`defaultMode` პროექტში:** ავტომატურ რეჟიმზე არ მოქმედებს. არ ვაყენებთ.

## შედეგები

- \+ აშკარა გზები (დამტკიცების თვითმინიჭება, ჟურნალის გადაწერა, კარიბჭეების გვერდის ავლა) იკეტება მიზეზის ახსნით.
- \+ მეორე სესია იმავე საქაღალდეში სხვის შეცდომაზე არ ფერხდება (Stop-gate მხოლოდ საკუთარ ფაილებს ამოწმებს).
- − ყოველ Edit/Write/Bash-ს ~0.3 წამი ემატება (გაზომილი 2026-09-19, საშუალოდ 10 გაშვებაზე; თითქმის მთლიანად Python-ის გაშვებაა).
- − harness-ის ყოველი ცვლილება მფლობელს ეკითხება — ეს განზრახ არის.

## დადასტურება

დრილი: სუფთა კონტროლები გადის (ჩვეულებრივი ფაილი, draft-ის რედაქტირება, `cat approve.py`, `git add memory/approvals.md`, ჩვეულებრივი push, commit-ის შეტყობინება „-n"-ით, `git commit -uno`, `env … git log`, `bash -c 'git status'`, `ls .env`, `git check-ignore .env`, `.env.example`-ის ჩაწერა); ყოველი G/B წესი თავისი მარკერით (`GUARD[G4]` …) ბლოკავს, მათ შორის შეფუთული და ჩადგმული ფორმებიც (`env git commit -n`, `bash -c 'git commit -n'`, `GIT_CONFIG_*`, `xargs git push -f`, `bash -c 'cat .env'`). ცოცხალი ტესტი: ჩადგმული `claude -p` სესია ცდილობს `intent.md`-ის სტატუსის შეცვლას და `.env`-ის წაკითხვას — ორივე უნდა დაიბლოკოს.
