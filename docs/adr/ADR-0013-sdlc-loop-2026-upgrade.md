# ADR-0013: სამუშაო ციკლის 2026-ის განახლება

## კონტექსტი

ძრავის ავტორმა (2026-10-30) იკითხა, რამდენად სწორია ძრავის ეტაპები 2026 წლის საუკეთესო პრაქტიკის მიხედვით, და სთხოვა მათი გაუმჯობესება. აქტუალური წყაროების შემოწმებამ (spec-driven development — GitHub Spec Kit, AWS Kiro; evaluation-driven development — Xia et al., arXiv 2411.13768, O'Reilly, Braintrust; აგენტის ციკლი Build→Test→Deploy→Monitor — LangChain) ერთი სურათი აჩვენა:

- **ძრავის ციკლი ([[ADR-0001-foundation-and-sdlc-loop]]) უკვე შეესაბამება დომინანტურ მიდგომას** — spec-driven development: სპეციფიკაცია ჭეშმარიტების წყაროა, თანმიმდევრობა Specify → Plan → Tasks → Implement, ადამიანის დამტკიცება ყოველ ზღვარზე (`/approve`). ძრავა ამ მხრივ წინ არის — უკვე აქვს დამტკიცების კარიბჭეები, guardrails და observability ([[ADR-0007-ai-security-and-observability]], [[ADR-0010-prompt-cache-and-cost]]).
- ორი ადგილას ძრავა 2026-ის პრაქტიკას ჩამორჩება. **პირველი:** evaluation-driven development ამბობს, რომ evals სპეციფიკაციასთან ერთად, ადრევე უნდა დაიწეროს და მუდმივად ეშვებოდეს — „evals არის სამუშაო სპეციფიკაცია". ძრავაში evals მხოლოდ L2 კარიბჭეა ([[ADR-0006-deterministic-gates-and-evals]]), ანუ გვიანდელი შემოწმება; [[ADR-0012-ai-product-foundation-guarantee]] მათ უკვე ნაგულისხმევ საძირკვლად აქცევს, მაგრამ „სად იწერება" დაუზუსტებელია. **მეორე:** ციკლი „ჩვენებაზე" ჩერდება — გაშვების შემდეგ დაკვირვებისა და უკუკავშირის ეტაპი არ არის, თუმცა 2026-ში ეს პირველი კლასის ფაზაა (ცოცხალი evals, ხარჯი, drift, და პროდაქშენის შეცდომა მომდევნო ციკლის ტესტად).

## გადაწყვეტილება

1. **evals სპეციფიკაციასთან ერთად (shift-left).** `/spec` skill გასაგები კითხვით ითხოვს წარმატების საზომსა და evals-ს; სპეციფიკაციის შაბლონს ემატება სექცია „წარმატების საზომი / evals"; ეს ხდება L2 eval-კარიბჭის კონტრაქტი ([[ADR-0006-deterministic-gates-and-evals]], [[ADR-0012-ai-product-foundation-guarantee]]). evals აღარ არის მხოლოდ ბოლო კარიბჭე — ის სპეციფიკაციის ნაწილია და ციკლში მუდმივად ეშვება.
2. **ახალი ეტაპი: „გაშვება + დაკვირვება" (deploy + observe + feedback).** „ჩვენება და პილოტის" შემდეგ ემატება ეტაპი, რომელიც ფარავს: ცოცხალში გაშვებას, პროდაქშენზე დაკვირვებას (ტრეისები და ხარჯი `/observatory`-ით — [[ADR-0007-ai-security-and-observability]], [[ADR-0010-prompt-cache-and-cost]]), ცოცხალ evals-ს, drift-ს და უკუკავშირის მარყუჟს — პროდაქშენის შეცდომა ახალ სპეციფიკაციად/ამოცანად ბრუნდება. ეტაპების გამტარი ([[ADR-0011-idea-first-stage-conductor]]) ამ ეტაპს ასახელებს; გაიდებს ემატება „deploy + observe" ნაწილი.
3. **რიგი უცვლელი რჩება (spec-first).** spec-driven development სპეციფიკაციას არქიტექტურამდე სვამს, ამიტომ ძრავის ახლანდელი რიგი (intent → spec → architecture → plan & build → show) სწორია და არ იცვლება. არქიტექტურული ADR-ები მაშინ იწერება, როცა ძნელად შესაქცევი გადაწყვეტილება ჩნდება (დიდი არჩევანი — სტეკი — იდეისთანავე, დანარჩენი საჭიროებისამებრ).

ეს ADR აფართოებს [[ADR-0001-foundation-and-sdlc-loop]]-ის ციკლს (არ ანაცვლებს — ADR-0001 ჯერ `proposed`-ია, გაყინული არ არის); დამტკიცებისას ADR-0001-ის ციკლის ჩამონათვალიც ამ ორი დამატებით განახლდება.

## განხილული ალტერნატივები

- **სრული გადაწყობა — ADR/PRD/TRD სპეციფიკაციამდე** (კლასიკური waterfall, როგორც ძრავის ავტორმა თავიდან დახაზა). უარყოფილია: spec-driven development (დომინანტური 2026 მიდგომა) სპეციფიკაციას წინ სვამს, არქიტექტურას კი დაგეგმვის ფაზაში; გადაწყობა ეტაპების გამტარს, გაიდებს, skill-ებსა და დრილის მიბმულ ტექსტებს (L-018) უმიზნოდ არევდა საუკეთესო პრაქტიკის მოგების გარეშე. PRD/TRD ცალკე მძიმე დოკუმენტებად 2026-ში აღარ იწერება — მათ ენაცვლება მსუბუქი `intent.md` + ADR-ები, რაც ძრავას უკვე აქვს.
- **ციკლი უცვლელად** (ADR-0001 ისე დავტოვოთ, როგორც არის). უარყოფილია: სწორედ ეს ორი ადგილი (shift-left evals, პროდაქშენის უკუკავშირი) ჩამორჩება 2026-ის პრაქტიკას.
- **სრული MLOps პლატფორმა** (დაფები, ავტო-გადავარჯიშება, serving infra ძრავაში ჩაშენებული). უარყოფილია: მძიმეა ნაკრების აუდიტორიისთვის (vibe-coder-ები, პატარა პროექტები); [[ADR-0012-ai-product-foundation-guarantee]]-ის ტექ-ნეიტრალურობა ამბობს, რომ ხელსაწყოს პროექტი ირჩევს. ძრავა უზრუნველყოფს პრაქტიკას (დააკვირდი + უკუკავშირი), არა კონკრეტულ პლატფორმას.

## შედეგები

- \+ ეტაპები სრულად შეესაბამება 2026-ის საუკეთესო პრაქტიკას (SDD + EDD + agent lifecycle).
- \+ evals ადრევე, სპეციფიკაციასთან იწერება — „POC purgatory" (მარადიული ექსპერიმენტი პროდუქტის გარეშე) თავიდან აცილებული.
- \+ ციკლი პროდაქშენამდე და უკუკავშირამდე გრძელდება; `/observatory` დაკვირვების საფუძველს უკვე აწვდის.
- − ცვლილება რამდენიმე კოორდინირებულ ადგილს ეხება ერთდროულად: ეტაპების გამტარი, ADR-0001-ის ციკლის ჩამონათვალი, გაიდები, `/spec` skill და შაბლონი, დრილის მიბმული ტექსტები (L-018) — ყველა ერთ ცვლილებაში უნდა დაემთხვას, თორემ „ერთი ნაბიჯი — ერთი ინსტრუქცია" ირღვევა.
- − „გაშვება + დაკვირვების" კონკრეტულ ხელსაწყოს პროექტი ირჩევს; ძრავა მას არ აშენებს (ტექ-ნეიტრალურობა).
