# ADR-0011: იდეით დაწყება — ეტაპების გამტარი და პირველი გაშვების თვითაწყობა

## კონტექსტი

**ძრავის ავტორი (2026-10-11):** „ეს ძრავა მინდა იყოს მზად, რომ როცა გაუშვებს ადამიანი ახალი, თავისი პროექტისთვის, პირდაპირ მისი ახალი იდეის … ინტეგრაცია დაიწყოს, პროცესს გააყოლოს ამ ძრავამ … საწყის setup-ს არ გაუშვებს ადამიანი, პირდაპირ ამ ძრავას დააყენებს და Claude Code-ს პირდაპირ მისწერს თავის იდეას" (მართლწერა გასწორებულია).

იმავე დღეს ნამდვილმა სესიამ ნაკრების ახალ ასლში, პირველი შეტყობინებით „მინდა გავაკეთო ვებსაიტი ჩემი საცხობისთვის", აჩვენა, რა უშლის ამას ხელს: ინტერვიუ თავისით დაიწყო, მაგრამ შაბლონები setup-ის ნაბიჯებსა და ძრავის ცხრა ADR-ის დამტკიცებას ითხოვდა; ახალ ასლში commit-ის შემოწმებები გამორთულია (`core.hooksPath` არ არის); gitleaks-ის გარეშე `secrets` gate ყოველ commit-ს INCONCLUSIVE-ით აჩერებს; განზრახვის შემდეგ ეტაპებს არაფერი ატარებს.

ეტაპები ძრავაში უკვე არსებობს — ეს არის [[ADR-0001-foundation-and-sdlc-loop]]-ის ციკლი (intent → spec → plan → code → gates → review) და [[plan]]-ის ფაზები F1–F5. ახალი ეტაპები არ გვჭირდება. გვაკლია **გამტარი** — რაღაც, რაც დოკუმენტების სტატუსებს კითხულობს და ადამიანსაც და აგენტსაც ეუბნება, სად დგას პროექტი და რა არის შემდეგი ნაბიჯი.

## გადაწყვეტილება

**1. ეტაპების გამტარი** (`py -3.12 tools/context_graph.py stage`). ის არაფერს წერს და არაფერს ინახავს: ყოველ ჯერზე თავიდან კითხულობს იმავე დოკუმენტებს, რომლებსაც კონტექსტის გრაფი ([[ADR-0003-context-graph-obsidian]]) — intent.md-ს, უახლეს სპეციფიკაციას, პროექტის ADR-ებს და ამ სპეციფიკაციის გეგმას — და ეტაპს ასე ადგენს:

| ეტაპი | როცა | შემდეგი ნაბიჯი |
|---|---|---|
| 1/5 განზრახვა | intent.md-ის §1 ცარიელია, ან intent `draft`-ია | ადამიანი იდეას წერს → `/intent` (ინტერვიუ) → `/approve intent` |
| 2/5 სპეციფიკაცია | intent `accepted`-ია, სპეციფიკაცია არ არის ან `draft`/`review`-ია | `/spec` → `/approve spec NNNN` |
| 3/5 არქიტექტურა | სპეციფიკაცია `approved`-ია, პროექტის არცერთი ADR არ არის `accepted` | `/adr` (სტეკი, ჰოსტინგი…) → `/approve adr NNNN` |
| 4/5 გეგმა და აშენება | პროექტის ADR `accepted`-ია; გეგმა არ არის, `draft`-ია ან სრულდება | `/feature-plan` → `/approve plan NNNN` → აშენება, gate-ები |
| 5/5 ჩვენება და პილოტი | გეგმა `done`-ია | შედეგის ჩვენება; ახალი ფუნქცია — ახალი `/spec` |

ეტაპი ჩანს სამ ადგილას: SessionStart-ის brief-ის თავში (აგენტისთვის — რას აკეთებს ადამიანი და რას აგენტი), statusline-ში (ადამიანისთვის) და `/approve`-ის პასუხში (რა მოდის დამტკიცების შემდეგ).

**2. ძრავის გადაწყვეტილებები რიგის გარეშე.** ძრავის საკუთარ ADR-ებს frontmatter-ში აქვს `scope: engine`. გამტარი მათ არ ითვლის, brief-ი მათ ერთ ხაზად აჩვენებს, `pending` კი — ცალკე ნაწილად: ისინი ძრავის ავტორის გადასაწყვეტია და ახალი პროექტის ეტაპებს არ აჩერებს. `scope`-ის ნებისმიერი სხვა მნიშვნელობა, გარდა `engine`-ისა და `project`-ისა, გრაფის შეცდომაა (SCOPE).

**3. პირველი გაშვების თვითაწყობა** (`.claude/hooks/firstrun.py`, SessionStart). თუ საქაღალდე git-ის რეპო არ არის — `git init`; თუ `core.hooksPath` არ არის — `.githooks` (მხოლოდ ამ რეპოში, `--local`; გლობალურ კონფიგს არასდროს ეხება — L-005). ამოწმებს git-ს, git-ის სახელსა და ელფოსტას (`user.name`, `user.email` — მათ გარეშე commit ვერ შეიქმნება), Python 3.12-სა და gitleaks-ს. ადამიანის საკუთარ `core.hooksPath`-სა და სხვა რეპოს შიგნით მდებარე პროექტს არ ცვლის — მხოლოდ ატყობინებს. როცა ყველაფერი რიგზეა, არაფერს ამბობს; სხვა შემთხვევაში მოკლე შენიშვნით ეუბნება აგენტს, რა გააკეთა და რა აკლია. ინსტრუმენტის ნაკლს ერთ რეპოში ერთხელ ამბობს (ნიშანი `.git/`-ის შიგნით), გამორთულ commit-ის შემოწმებებს კი — ყოველ სესიაზე, სანამ არ ჩაირთვება. არაფერს აყენებს — ინსტრუმენტის დაყენება ადამიანის „კი"-ა.

**4. საიდუმლოების შემოწმება gitleaks-ის გარეშე.** თუ gitleaks ვერ მოიძებნა და `GITLEAKS_BIN` ცალსახად არ არის მითითებული, `secrets` gate იმავე ფაილებს ძრავის საკუთარი სკანერით ამოწმებს (`tools/redact.py` — იგივე სია, რომლითაც sentinel მუშაობს), და შედეგის ხაზი ამას პირდაპირ წერს: ძრავის სკანერია, gitleaks არ არის, git-ის ისტორია არ შემოწმდა. ცალსახად მითითებული, მაგრამ არარსებული `GITLEAKS_BIN` ისევ INCONCLUSIVE-ია (ძრავის ავტორის არჩევანი).

**5. იდეა პირველივე შეტყობინებიდან.** CLAUDE.md-ში: თუ ადამიანის შეტყობინება იდეაა (საიტი, თამაში, აგენტი, ავტომატიზაცია…), აგენტი setup-ს არ ითხოვს — `/intent` იდეას მაშინვე ჩაწერს intent.md-ის §1-ში ადამიანის სიტყვებით და ინტერვიუს იწყებს. იქვეა ქართულის ხარისხის მოკლე წესი, რადგან ძრავა ავტორის გლობალურ კონფიგურაციას არ ეყრდნობა.

**6. ნაკრების შაბლონები.** intent.md — ცარიელი §1-ით („დაწერე შენი იდეა") და ძრავის პრინციპების გარეშე (ისინი ADR-ებშია); plan.md — F1–F5; progress.md და todo.md — setup-ის ნაბიჯების გარეშე; README — სამი ნაბიჯი.

**7. პროექტის ტიპი და მისი სახელმძღვანელო** (ფაზა 2). intent.md-ის frontmatter-ში `kind:` — website / game / agent / automation / other (სხვა მნიშვნელობა — KIND შეცდომა). თითო ტიპს თავისი სახელმძღვანელო აქვს — `docs/guides/<kind>.md`: §1 ინტერვიუს კითხვები, §2 სტეკის 2–3 ვარიანტი ხუთი ბრძანებით (install · run · lint · test · show), §3 პირველი ვერსიის ფარგლები, §4 შედეგის ჩვენება, §5 ხაფანგები. გამტარი ყოველ ეტაპზე შესაბამის ნაწილს ასახელებს; ტიპი ჯერ თუ არ არის ჩაწერილი, ჯერ მას ითხოვს. მე-4 ეტაპზე, როცა `lint` და `unit` ორივე გამორთულია, აგენტს ჯერ კოდის შემოწმებების ჩართვას ეუბნება — სტეკის ADR-ის ბრძანებებით, მხოლოდ პროექტის საკუთარ კოდზე (ADR-0006-ის `ruff`/`pytest` მხოლოდ Python-ის მაგალითია). საქაღალდე, რომელსაც თავისი `package.json` ან `pyproject.toml` აქვს, პროდუქტის კოდია: მისი Markdown გრაფის შემოწმებაში არ შედის, `node_modules`, `dist`, `build` და მსგავსი კი ნებისმიერ სიღრმეზე გამოტოვებულია.

## განხილული ალტერნატივები

- **ახალი ეტაპების სისტემა ან მდგომარეობის ფაილი**, რომელშიც skill-ები ეტაპს წერენ — ერთი და იმავე ფაქტისთვის მეორე წყარო გაჩნდებოდა, ხელით ან `/approve`-ით შეცვლილი სტატუსის შემდეგ კი ის მოძველდებოდა. სტატუსები უკვე ერთადერთი წყაროა — უარყოფილია.
- **setup-ის სკრიპტი, რომელსაც ადამიანი პირველად უშვებს** — ძრავის ავტორის მიზანი setup-ს პირდაპირ გამორიცხავს, და სკრიპტის დავიწყება შეიძლება; SessionStart-ის hook იგივეს თავისით აკეთებს — უარყოფილია.
- **gitleaks-ის გარეშე INCONCLUSIVE-ის დატოვება** — ახალ კომპიუტერზე ყოველი commit გაჩერდებოდა; ძრავის ავტორმა მონიშნული შემცვლელი აირჩია — უარყოფილია.
- **ძრავის ADR-ების `accepted`-ად მონიშვნა ნაკრებში** — დამტკიცება მხოლოდ მფლობელის `/approve`-ია (არცერთი აგენტი არაფერს ამტკიცებს), და ისინი მაინც პროექტის ჯაჭვში დარჩებოდა — უარყოფილია; `scope` ველი ორივე პრობლემას ხსნის.

## შედეგები

**+** ახალი ადამიანი პირველივე შეტყობინებიდან თავის იდეაზე მუშაობს; ყოველ სესიაში და statusline-ში ჩანს, რომელ ეტაპზეა პროექტი და რა მოდის შემდეგ; commit-ის შემოწმებები თავისით ირთვება; `/approve` ამბობს, რა არის შემდეგი ნაბიჯი.

**−** შემცვლელ სკანერს entropy-ის ზღვარი არ აქვს და git-ის ისტორიას არ ამოწმებს — gitleaks-ზე სუსტია, და ეს შედეგში წერია. სესიის დაწყებას ერთი hook ემატება (~0.3 წმ). წესი „3/5 დასრულებულია, როცა პროექტის ერთი ADR მაინც `accepted`-ია" დიდი პროექტისთვის შეიძლება უხეში იყოს — ტიპის სახელმძღვანელოებთან ერთად გადაიხედება. `scope: engine` ძრავის ყოველ ახალ ADR-ს უნდა დაეწეროს.

## დადასტურება

- დრილი: გამტარის ყოველი მდგომარეობა (ცარიელი §1, `draft` intent, `draft` სპეციფიკაცია, დამტკიცებული სპეციფიკაცია ADR-ის გარეშე, `proposed` პროექტის ADR, `draft` გეგმა, მიმდინარე გეგმა, `done` გეგმა); ძრავის ADR-ები ეტაპს არ ცვლის; არასწორი `scope` → SCOPE; `/approve` შემდეგ ეტაპს ასახელებს; statusline ეტაპს აჩვენებს; პირველი გაშვება (რეპოს გარეშე → `git init` და `core.hooksPath`; უკვე აწყობილი → სიჩუმე; სახელის, ელფოსტის, git-ის ან gitleaks-ის ნაკლი → შენიშვნა, ერთხელ; გამორთული შემოწმებები → შენიშვნა ყოველ სესიაზე; სესია არასდროს ჩავარდება); შემცვლელი სკანერი (სუფთა → PASS წარწერით, გასაღები → FAIL, ცალსახად მითითებული და არარსებული gitleaks → INCONCLUSIVE).
- ნამდვილი სესია (L-016): ნაკრების ახალი ასლი, პირველი შეტყობინება — საიტის იდეა; რამდენიმე-ტურიანი `claude -p` სპეციფიკაციამდე მიდის და setup-ს არ ითხოვს.
