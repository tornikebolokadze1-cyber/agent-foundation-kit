# ADR-0001: საძირკველი და სამუშაო ციკლი

## კონტექსტი

ძრავა იმ მფლობელისთვისაა, რომელიც კოდს არ კითხულობს და პროექტს Claude Code-ით აშენებს. ძრავის ავტორის მოთხოვნა (2026-09-18, [[intent]] P1, P5): პროექტი თავიდანვე უნდა დაიწყოს 2026 წლის საუკეთესო პრაქტიკით, და სპეციფიკაცია დაგეგმვაზე მხოლოდ მისი თანხმობის შემდეგ უნდა გადავიდეს. Anthropic-ის „AI-native SDLC playbook" იგივე ჯაჭვს გვთავაზობს: განზრახვა → სპეციფიკაცია → გეგმა → შესრულება → შემოწმება → review, სადაც ყოველ რგოლს თავისი ფაილი აქვს. საფრთხე ისაა, რომ მოდელი თავად „დაამტკიცებს" საკუთარ ნამუშევარს, ან ერთი და იგივე რამ რამდენიმე ადგილას ეწერება და ერთმანეთს ეწინააღმდეგება.

## გადაწყვეტილება

1. **ჯაჭვი და მისი ფაილები:** `intent.md` (ერთი, ფესვში) → `docs/specs/SPEC-NNNN-*.md` → `docs/plans/PLAN-NNNN-*.md` → კოდი → კარიბჭეები (gates) → review ([[REVIEW]] წესებით). პროექტის დიდი რუკა — `plan.md`, მდგომარეობა — `progress.md`, გადაწყვეტილებები — `docs/adr/`.
2. **დამტკიცება მხოლოდ მფლობელისაა:** სტატუსებს `accepted` / `approved` / `rejected` / `superseded` ანიჭებს მხოლოდ `tools/approve.py`, რომელსაც მფლობელის `/approve` skill უშვებს. ყოველი დამტკიცება იწერება `memory/approvals.md`-ში. წინაპირობები მანქანურად მოწმდება: სპეციფიკაცია მხოლოდ დამტკიცებულ intent-ზე, გეგმა მხოლოდ დამტკიცებულ სპეციფიკაციაზე.
3. **დამტკიცებული გაყინულია:** შეცვლა = ჯერ ხელახლა გახსნა (status → draft), მერე ხელახალი დამტკიცება; ADR საერთოდ არ იცვლება — ახალი ADR ანაცვლებს (`supersedes`).
4. **ენა:** მფლობელისთვის განკუთვნილი ყველაფერი (intent, specs, plans, ADR, progress, README) — ქართულად; აგენტისთვის განკუთვნილი ინსტრუქციები (CLAUDE.md, AGENTS.md, skills, rules, prompts) — ინგლისურად, რადგან ასე ზუსტია და ორჯერ ნაკლებ ტოკენს ხარჯავს. იდენტიფიკატორები, გზები, ბრძანებები — ყოველთვის ინგლისურად.
5. **ინსტრუმენტები:** პროცესი ცხოვრობს პროექტის skill-ებში (`/intent`, `/spec`, `/feature-plan`, `/adr`, `/approve`, `/session-close`, `/reflect`, `/orchestrate`). სახელები არ ემთხვევა გლობალურ skill-ებს (გლობალური უპირატესობით იტვირთება).
6. **git:** მუშაობა ბრანჩზე, CHECKPOINT-ფორმატის commit-ები, `main`-ში შერწყმა მფლობელის გადამოწმების შემდეგ. სხვა სესიის ან გარედან შემოტანილი მასალა (`research/`) ხელშეუხებელია — „foreign" ზონაა.

## განხილული ალტერნატივები

- **GitHub Spec Kit** (`specify init`): კარგი და აქტიური, მაგრამ მესამე დაგეგმვის სისტემა იქნებოდა (Claude Code-ს უკვე აქვს plan რეჟიმი, plugin-ებს კი — საკუთარი დაგეგმვის skill-ები), დამატებით `uv`-ს მოითხოვს და მფლობელის დამტკიცების კარიბჭე არ აქვს. უარყოფილია; მისი კარგი იდეები (constitution, acceptance criteria) ჩვენს შაბლონებშია.
- **ერთი დიდი CLAUDE.md ყველაფრით:** მარტივია, მაგრამ 200 ხაზზე მეტი კონტექსტს ანაგვიანებს და ფაქტი ორ ადგილას ძველდება. უარყოფილია.
- **დამტკიცება მოდელის skill-ით:** მოდელს შეეძლებოდა თავად გამოეძახა. უარყოფილია — `/approve` owner-only-ია (`disable-model-invocation`).

## შედეგები

- \+ ყოველ ნაბიჯს ერთი ფაილი და ერთი მფლობელი აქვს; მოდელი საკუთარ ნამუშევარს ვერ ამტკიცებს.
- \+ ჯაჭვის დარღვევას (მაგ. გეგმა დაუმტკიცებელ სპეციფიკაციაზე) gate იჭერს, არა კარგი ნება.
- − მფლობელს მეტი დამტკიცება უწევს; `/approve` (არგუმენტის გარეშე) აჩვენებს, რა ელოდება.
- − guard „სიჩქარის ბორცვია" და არა საკეტი — იხ. [[ADR-0004-harness-permissions-hooks-guard]].
