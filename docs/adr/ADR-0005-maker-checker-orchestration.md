# ADR-0005: ორკესტრაცია ორ ეტაპად

## კონტექსტი

ორკესტრაცია (რამდენიმე მოდელის შეთანხმებული მუშაობა) აქ maker/checker წყვილს ნიშნავს: ერთი მოდელი ქმნის (maker), მეორე ამოწმებს (checker). ერთი და იმავე მოდელის ორჯერ გაშვება „მეორე აზრი" არ არის — ორივე გაშვებას ერთი და იგივე ბრმა წერტილები აქვს. დამოუკიდებლობის წყაროები, ძალის მიხედვით: დეტერმინისტული შემოწმება (exit code, [[ADR-0006-deterministic-gates-and-evals]]), სხვა ოჯახის მოდელი, იმავე ოჯახის სხვა მოდელი, სხვა ჩარჩო (ახალი კონტექსტი და შემოწმების სხვა წესები).

2026-09-18-ის ვერსია (ძრავის ავტორის მაშინდელი მოთხოვნით): არქიტექტურა — Claude Fable 5.1 ↔ ChatGPT Astra, ერთი ბრუნი; კოდი — Claude Opus 5 ↔ ChatGPT Sol, მაქსიმუმ ორი ბრუნი; ChatGPT — გამოწერის ავტორიზაციით.

**ძრავის ავტორი (2026-10-09)** ამ ვერსიას ცვლის: „დასაწყისში ორკესტრირებული იქნება მხოლოდ და მხოლოდ კლოდის 3 მოდელი: Claude Opus 5.5, Claude Sonnet 5.5 და Claude Haiku 5.5. ხარისხიანი შედეგის მისაღებად ხელმისაწვდომ ფასებად. შემდეგ ეტაპებზე კი განვიხილავ Fable-ის მოდელის ჩართვასაც, GPT-ისა და სხვა მოდელების დამატებებსაც" (ციტატაში მხოლოდ მართლწერაა გასწორებული). როლების ორი ვარიანტიდან ავტორმა აირჩია „Sonnet წერს, Opus ამოწმებს" (2026-10-09).

ფასები 1M ტოკენზე (შემავალი / გამომავალი), Anthropic-ის ფასების ცხრილით, 2026-10-06-ის მდგომარეობით: Haiku 5.5 — $0.10 / $0.50 (100K ტოკენამდე prompt-ზე), Sonnet 5.5 — $2 / $10, Opus 5.5 — $4 / $20, Fable 5.1 — $10 / $50. ორკესტრაცია `claude -p`-ით მფლობელის გამოწერაზე მუშაობს, ამიტომ ცალკე ანგარიში არ მოდის — ცხრილი მოდელების შედარებით „წონას" აჩვენებს.

## გადაწყვეტილება

1. **ორი ეტაპი.** `orchestration/config.toml`-ში `stage = 1` — მუშაობს მხოლოდ Claude. II ეტაპზე გადასვლა (`stage = 2`) მფლობელის გადაწყვეტილებაა, დაცული ფაილის ცვლილებით. სანამ `stage = 1`-ია, `run.py` არა-Claude მოდელს არ გაუშვებს (exit 5) — წესს მანქანა იცავს და არა დაპირება.
2. **I ეტაპის როლები:**

   | ციკლი | maker (ქმნის) | checker (ამოწმებს) | ბრუნები | რას აბრუნებს |
   |---|---|---|---|---|
   | არქიტექტურა — `run.py arch` | Opus 5.5 — წინადადება და ბოლოს სინთეზი | Sonnet 5.5 — აუდიტი და საკუთარი პოზიცია | 1 | ADR-ის პროექტი (`proposed`); გადაწყვეტს მფლობელი |
   | კოდი — `run.py code-check` | Sonnet 5.5 — თავად ინტერაქტიური სესია, თავიდანვე Sonnet-ზე გაშვებული | Opus 5.5 — კითხულობს diff-ს, სპეციფიკაციას და [[REVIEW]]-ს | მაქს. 2 | `VERDICT: approve / changes-requested / blocked` |
   | რუტინა | Haiku 5.5 — ძებნა, დახარისხება, ინგლისური შეჯამება, მექანიკური ცვლილება (subagent-ები `model: haiku`) | დეტერმინისტული gate-ები | — | — |

   სესიის მოდელი დასაწყისში ირჩევა (პირველ შეტყობინებამდე `/model sonnet`) და შუაში არ იცვლება: prompt cache (წინა კონტექსტის შენახული ასლი) მოდელზეა მიბმული — Anthropic-ის დოკუმენტაციით, კეში მოდელის ფარგლებშია — ამიტომ `/model`-ით გადართვა მთელ კონტექსტს თავიდან აწერინებს. პარალელურმა სესიამ ამ პროექტის ერთ ტრანსკრიპტში ორ ასეთ გადართვაზე 136K და 299K ტოკენის ხელახალი ჩაწერა გაზომა (მეორადი წყარო, 2026-10-09). სხვა მოდელის საქმე subagent-ს ან `claude -p`-ს გადაეცემა.

   მოდელების იდენტიფიკატორები (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`) ერთ ადგილას წერია — `config.toml`-ში. Haiku 5.5 ქართულ ტექსტს, რომელსაც ადამიანი კითხულობს, არ წერს: Haiku 4.5-მა ქართულში 2.6/5 მიიღო (L-006), Haiku 5.5 ჯერ გაზომილი არ არის (P-005).
3. **როგორ იძახება.** `run.py`-ის მიერ გაშვებული Claude-ის ყოველი ნაბიჯი — `claude -p --model <id> --restricted`, მხოლოდ კითხვის ინსტრუმენტებით (`Read, Grep, Glob`), ერთ გამოძახებაზე ხარჯის ზღვრით (`--max-budget-usd`) და `EPISODIC_NESTED=1`-ით. `--restricted` პროექტის პარამეტრებს არ კითხულობს, ამიტომ `run.py` საიდუმლო ფაილების `Read` deny წესებს `--settings`-ით თავიდან გადასცემს; ჩადგმულ პროცესს სხვა სერვისების გასაღებები არ გადაეცემა, prompt-ები და პასუხები კი `tools/redact.py`-ზე გადის. `--restricted` ფაილის ინსტრუმენტებს სამუშაო საქაღალდით ზღუდავს — 2026-10-18-ს ცოცხლად გაიზომა: საქაღალდის გარეთა ფაილიც და მის გარეთ გამავალი ბმულიც (junction) უარყოფილი იყო; ამიტომ deny წესებს მხოლოდ პროექტის შიგნით არსებული საიდუმლო ფაილები რჩება დასაცავი. საიდუმლო ფაილის სახეები ერთ ცხრილშია (`run.py`, `SECRET_KINDS`): მისგანაა აგებული ჩადგმული გამოძახების deny წესებიც და ის შემოწმებაც, რომელიც ასეთ ფაილს prompt-ში არ უშვებს. checker ახალ კონტექსტში იწყება: maker-ის საუბარს ვერ ხედავს — მხოლოდ შედეგს, სპეციფიკაციას და [[REVIEW]]-ს. მისი პასუხის ბოლო ხაზი ზუსტად `VERDICT: …` ან `POSITION: …` უნდა იყოს; თუ არ არის, გაშვება ჩავარდნილია და ბრუნს არ ხარჯავს. config-ში ყოველი მოდელი იწერება ფორმით `პროვაიდერი:მოდელი` (მაგ. `claude:claude-opus-5-5`), ამიტომ ახალი მოდელის დამატება ერთი ხაზის ცვლილებაა.
4. **II ეტაპი — ჩაწერილია, ჩართული არ არის.** კანდიდატები: Claude Fable 5.1 (`claude-fable-5-1`) დიდ არქიტექტურულ გადაწყვეტილებებზე; ChatGPT Astra (`gpt-6-astra`) და Sol (`gpt-5.6-sol`) — სხვა ოჯახის checker-ები, Codex CLI-ით და ChatGPT-ის გამოწერით (`codex login`, API გასაღების გარეშე, `-s read-only`); სხვა მოდელები (მაგ. Gemini) — ახალი პროვაიდერით. Codex-ის გზა კოდში რჩება და მას dry-run-ით ამოწმებს დრილი (`tools/gates/drill.py`, ჯგუფი `orchestration`, იხ. „დადასტურება"), რომ II ეტაპზე გადასვლისას მზად დახვდეს. რომელი კანდიდატი, რომელ როლში — მფლობელი წყვეტს; ამ ADR-ის დამტკიცების შემდეგ ეს ახალი ADR იქნება (`supersedes`). II ეტაპის ADR-მა ერთი რამ აუცილებლად უნდა გადაწყვიტოს: `codex exec -s read-only` ჩაწერას კრძალავს, კითხვას — არა, და Claude-ის `Read` deny წესების მსგავსი სია Codex-ს არ აქვს; ამიტომ ChatGPT-ის checker-ს საიდუმლო ფაილების (`.env`, გასაღებები) წაკითხვა და OpenAI-სთვის გაგზავნა შეეძლება. გარემოს ცვლადებიდან გასაღებები მას `tools/claude_cli.py`-ის იგივე ფილტრით არ მიდის, ფაილებს კი ეს ფილტრი ვერ იცავს. ეს ფილტრი სახელების სიაა და ყველა სახელს ვერ იცნობს; ნაბიჯისთვის, რომელსაც ბრძანებების გაშვება შეუძლია (codex), II ეტაპის ADR-მა ის ნებადართულის სიით (allowlist) უნდა შეცვალოს.
5. **ჩანაწერები:** ყოველი გაშვება → `orchestration/runs/<თარიღი>-<ციკლი>-<თემა>/` (prompt-ები, პასუხები, `meta.json` ეტაპით, მოდელებითა და თითო ნაბიჯის ფასით); git-ში ინახება, და ბრუნების ლიმიტი სწორედ ამ ჩანაწერებიდან ითვლება.
6. **გამორთულია:** `enabled = false`. სანამ ასეა, `run.py` მხოლოდ `status`-სა და `--dry-run`-ს ასრულებს. ჩართვა მფლობელის გადაწყვეტილებაა (P-001), დაცული ფაილის ცვლილებით.
7. **კარიბჭეები ციკლზე მაღლა დგას:** checker-ის „approve" ჩავარდნილ gate-ს ვერ გადაფარავს.
8. **ვინ რა დავალებას იღებს**, შეიძლება შესთავაზოს decision model-მა (დისპეჩერმა) — [[ADR-0009-decision-model-dispatcher]]. მის გარეშეც ყველაფერი მუშაობს: ნაგულისხმევი ზოლი კოდია (Sonnet 5.5).

## განხილული ალტერნატივები

- **2026-09-18-ის ვერსია ახლავე (Fable ↔ Astra, Opus ↔ Sol):** დამოუკიდებლობით უფრო ძლიერია (სხვა ოჯახი), მაგრამ ორი გამოწერა და ორი CLI სჭირდება, Fable 5.1 კი Opus 5.5-ზე 2.5-ჯერ ძვირია. ავტორმა ის მეორე ეტაპზე გადაიტანა — რჩება II ეტაპის კანდიდატად.
- **„Opus წერს, Sonnet ამოწმებს":** შექმნის ხარისხი მაღალია, მაგრამ ყველაზე დიდი მოცულობა (კოდის წერა) ყველაზე ძვირ მოდელზე მოდის, შემმოწმებელი კი შემქმნელზე სუსტი გამოდის. ავტორმა არ აირჩია (2026-10-09).
- **ერთი მოდელი ყველგან (მხოლოდ Opus 5.5):** მარტივია, მაგრამ checker შემქმნელის ასლი იქნებოდა — იგივე ბრმა წერტილებით — და ყველაზე ძვირიც. უარყოფილია.
- **API გასაღებებით პირდაპირი გამოძახება:** ძრავა Claude-ის გამოწერით მუშაობს, API კი ცალკე ანგარიშია, სადაც ყოველ ტოკენში იხდი. უარყოფილია (როგორც 2026-09-18-ს).

## შედეგები

- \+ ერთი გამოწერა და ერთი CLI; ყველაზე დიდი მოცულობა (კოდის წერა) საშუალო ფასის მოდელზეა, ყველაზე ძლიერი მოდელი შემოწმებასა და არქიტექტურას ემსახურება, მექანიკური საქმე კი Sonnet-ზე 20-ჯერ იაფ Haiku-ზე გადადის.
- \+ მოდელის შეცვლა და II ეტაპზე გადასვლა config-ის ცვლილებაა და არა კოდის.
- − **I ეტაპზე checker იმავე ოჯახიდანაა**, ამიტომ დამოუკიდებლობა უფრო სუსტია, ვიდრე Astra/Sol-ით იქნებოდა. კომპენსაცია: სხვა მოდელი (Opus ≠ Sonnet), სხვა ჩარჩო (ახალი კონტექსტი, [[REVIEW]]-ის სკალა) და, უპირველესად, დეტერმინისტული კარიბჭეები. II ეტაპი სხვა ოჯახის checker-ს დააბრუნებს.
- − კოდის maker-ი ინტერაქტიური სესიაა: რომელ მოდელზე მუშაობს, მფლობელი სესიის დაწყებისას ირჩევს. `run.py` ამას ვერ შეამოწმებს — `meta.json`-ში მხოლოდ config-ის მოდელს წერს.
